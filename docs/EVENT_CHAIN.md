# Проверяемый журнал и будущая интеграция

Новая запись — journal v2; чтение v1 сохранено. Правила игры по-прежнему v1. Ни отдельной блокчейн-сети, ни сетевых транзакций здесь нет.

## Событие

`journalVersion`, `eventId`, `gameNumber`/`gameId`, `seq`, `timestamp`, `timeSource`, `prevHash`, `hash`, `rollId`, `actor`, `type`, `payload`; действия и пропуски дополнительно содержат `decisionMaker`.

- `seq`: непрерывный номер от 0 внутри партии.
- `gameNumber`: идентификатор партии; для web используется UUID, для воспроизводимых симуляций — идентификатор seed. При создании новой независимой партии вызывающая система должна предоставить новый gameId; воспроизведение той же партии сохраняет его.
- `eventId`: SHA-256 канонического `{gameId,seq}`, уникальный для позиции в журнале партии. Повторное воспроизведение сохраняет ID, дубликаты внутри партии отклоняются.
- `timestamp`: ISO-8601 UTC. UI и CLI вводят реальное время через внешний clock. Чистое ядро по умолчанию использует детерминированное логическое время с отметкой `timeSource:logical`; оно не выдаётся за время настенных часов.
- `prevHash`: хеш предыдущего события; у первого — 64 нуля.
- `hash`: SHA-256 от UTF-8 канонического JSON всех полей события, кроме самого hash. Ключи объектов сортируются, массивы сохраняют порядок. Метаданные автора, времени и идентификаторов тоже связаны хешем.

События неизменяемы после создания. Приложение только добавляет записи. Replay проверяет цепочку, версию, ID, структуру времени и заново выполняет команды движка, сравнивая производные сбития, фиксации и победу. Recorded clock позволяет точно воспроизводить реальные timestamps, не сверяясь с текущими часами.

Порядок определяется seq. Внешние часы могут быть одинаковыми у нескольких событий или идти назад; это не меняет порядок игровых действий. Без подписанного доверенного источника timestamp не является доказательством реального времени.

## Контрольная запись

`checkpoint` содержит schemaVersion, gameId, eventCount, lastSeq, headHash, hashAlgorithm и canonicalization. Сравнение с независимо сохранённой контрольной записью обнаруживает обрезание хвоста и полную подмену журнала. Контрольный хеш, сохранённый рядом с журналом и заменённый вместе с ним, не обеспечивает независимого доверия.

```bash
npm run audit -- --input game.jsonl --output checkpoint.json
npm run audit -- --input game.jsonl --checkpoint checkpoint.json
```

В UI доступна кнопка «Контрольный хеш». Проверка CLI включает replay правил, а не только SHA-256.

## Контракт будущего адаптера

1. Получить валидированный checkpoint без изменения журнала и игровых правил.
2. Подписать party ID, eventCount, headHash, версию правил и геометрический commitment идентификатором организатора/участника.
3. Передать checkpoint адаптеру собственной сети. Сырые данные, партии и датасеты хранить отдельно; публикация хеша не требует публикации персональных данных.
4. Сохранить внешний receipt (networkId, transactionId, blockId, signer, checkpoint). Верификатор проверяет подпись/receipt, затем checkpoint и локальный replay.
5. При продолжении журнала публиковать новое завершение с прежним gameId и ссылкой на предыдущий checkpoint; повторные ID и конкурирующие ветви явно разрешать по протоколу сети.

Эти границы позволяют заменить транспорт и консенсус без вмешательства в Engine. Адаптер, подписи, сеть и доказательство честности организатора сейчас не реализованы. Seed не доказывает непредвзятость его выбора; цепочка сама по себе не препятствует пересозданию всей истории. Проверка правил отвергает нелегальную подмену даже при пересчитанных хешах, но другую полностью легальную историю можно обнаружить только по внешнему commitment.
